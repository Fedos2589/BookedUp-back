## Decisions (2026-11-26)

User's (don't re-ask):

- **D1** One VPS, Ubuntu 24.04, 2 vCPU / 4 GB, Docker Compose, Caddy in front with automatic HTTPS. No
  Kubernetes, Swarm, Terraform, PaaS, multi-region; monitoring is logs plus one uptime ping.
- **D2** One domain for everything: the front's static files on `/`, the API on `/api` with the prefix
  stripped (as the front's `vite.config.ts` proxy does). Why: the back's CSRF check refuses writes from another
  origin, and the session cookies are `__Host-*`.
- **D3** Postgres 18, Redis, the API, the notifications worker (one process).
- **D4** Telegram is required (no bot → no online booking, E7b D7): token and username from @BotFather,
  `TELEGRAM_WEBHOOK_SECRET` set, webhook per `docs/notifications.md`. WhatsApp, email, Web Push stay **off**.
- **D5** Production env: `NODE_ENV=production`, `APP_URL=https://<domain>`, `TRUST_PROXY=1`,
  `SESSION_COOKIE_SECURE=true`. Secrets never in git.
- **D6** Deploys are started by hand. No auto-deploy from `main`.

Made while splitting (check in the PR):

- **D7 Images are built on GitHub Actions and pushed to GHCR; the server only pulls.** A `Release` workflow
  (`workflow_dispatch`, from `main` only) in each repo pushes `ghcr.io/fedos2589/bookedup-api:<sha>` and
  `ghcr.io/fedos2589/bookedup-web:<sha>`, `linux/amd64`. Why not build on the server: `npm ci` + `tsc` + `vite build`
  of two repos on 4 GB next to a running Postgres can run out of memory, the server would need git, Node and the
  sources, and a rollback would mean rebuilding an old commit. With images a rollback is «pull the previous sha»,
  seconds. The repos are public, so the packages are made public once (R2) and the server pulls without a token.
  The server is **x86 (amd64)**, not ARM: one platform, no multi-arch build.
- **D8 The notifications worker runs inside the one API container** (`NOTIFICATIONS_WORKER=true`, the default).
  One container = one process = one worker. A separate worker container would need a second copy of the API with
  the worker on and the first one's off — no gain at this size.
- **D9 Migrations run from the API image itself:** `prisma` and `dotenv` (which `prisma.config.ts` imports) move
  to `dependencies`, the image keeps `prisma/` and `prisma.config.ts`, and the deploy runs
  `docker compose run --rm api npx prisma migrate deploy` before starting the new API. One image, one tag; a
  separate migrate image would double what Release pushes and what a rollback has to match.
- **D10 `btree_gist` needs no extra grant.** The compose Postgres user (`POSTGRES_USER`) is the cluster's superuser,
  and `btree_gist` is a trusted extension anyway (Postgres ≥ 13), so `CREATE EXTENSION` in
  `20261111134528_schedule` runs under `migrate deploy`. S1's check proves it on an empty database.
- **D11 The web image is `caddy:2-alpine` with the front's `dist/` in `/srv`;** the Caddyfile lives in the back's
  `deploy/` (next to the compose file and the domain) and is mounted. One proxy container: it serves the static
  files and proxies `/api`.
- **D12 Swagger stays reachable at `https://<domain>/api/docs-json`.** The back serves it at `/api/docs*` on its
  own (`main.ts`), so Caddy passes `/api/docs*` through **without** stripping; everything else under `/api/` is
  stripped. (Hiding it is open question 2.)
- **D13 Deploy is one command from the laptop:** `deploy/deploy.sh deploy@<ip> [api-sha] [web-sha]` copies
  `deploy/` (never `.env`), pulls, migrates, restarts, waits for health, logs the release. Rollback = the same
  command with the previous shas from `releases.log`. **Migrations are not rolled back:** rolling back across a
  migration that the old code can't read means restoring a backup (`docs/deploy.md`).
- **D14 Backups:** `pg_dump -Fc` nightly by cron into `/var/backups/bookedup`, 14 days kept, plus Hetzner's
  server backups (R3). A restore check restores a dump into a scratch database and counts rows. Off-site copies
  are open question 1.
- **D15 A separate Telegram bot for the server.** Setting a webhook turns `getUpdates` off, and the dev API polls
  (`telegram-polling.ts`): one bot can't serve both.

## Shape

```
Internet ──443/80──▶ web (Caddy, image bookedup-web: /srv = front dist, Caddyfile from deploy/)
                        ├─ /api/docs*  ─────────────▶ api:3000 /api/docs*      (as is)
                        ├─ /api/*      ─strip /api─▶ api:3000 /*               (incl. /telegram/webhook)
                        └─ /*          ─▶ /srv files, else /index.html (not for /assets/*)
api (bookedup-api, NOTIFICATIONS_WORKER on) ──▶ postgres:5432 (volume)   redis:6379 (volume, AOF)
no ports published except web's 80, 443 (tcp) and 443/udp
```

Server layout: `/opt/bookedup/{compose.yml,Caddyfile,.env.example,backup.sh,restore-check.sh}`
(copied by `deploy.sh`), `/opt/bookedup/.env` (secrets, mode 600, written once by hand), `/opt/bookedup/releases.log`,
`/var/backups/bookedup/`.

## Global constraints

- Nothing in `src/` changes. If a task finds it must, stop: it is a separate task.
- No secret in git: `deploy/.env.example` holds names and comments only; `.env` is in `.gitignore` already.
- Images: `ghcr.io/fedos2589/bookedup-api:<full sha>`, `ghcr.io/fedos2589/bookedup-web:<full sha>`, lowercase owner.
- Every shell script: `#!/usr/bin/env bash`, `set -euo pipefail`, a usage line on wrong arguments, passes
  `bash -n` and `shellcheck` (if `shellcheck` is not installed, say so in the commit message's body).
- Compose files: every service `restart: unless-stopped` and the json-file log driver with `max-size: 10m`,
  `max-file: 5`.
- Checks need Docker running locally. Commit messages via `git commit -F - <<'EOF'`.

## Review focus (for the Opus review of both PRs)

1. **Docker publishes ports past ufw.** Only `web` may have `ports:`; postgres and redis none. A `ports:` on them
   would be open to the internet whatever ufw says.
2. **CSRF and the real client IP through Caddy:** `reverse_proxy` keeps the `Host` header (the back compares
   `Origin` with it) and sets `X-Forwarded-For` itself, ignoring a client's one (no `trusted_proxies`) — so with
   `TRUST_PROXY=1` rate limits count by the real IP and a client can't pick its own.
3. **The SPA fallback must not hide a missing chunk:** after a deploy an old tab asks for an old
   `/assets/x-<hash>.js`; it must get 404, not `index.html` with 200 (a MIME error, a blank page). `index.html`,
   `sw.js`, `workbox-*.js`, `push-sw.js`, `manifest.webmanifest` are `no-cache`, so the PWA sees new versions.
4. **The Postgres password inside `DATABASE_URL`:** generated as hex (`openssl rand -hex 24`), so it needs no URL
   escaping; the compose file builds the URL from `POSTGRES_PASSWORD`, not a second copy of it.
5. **Release from a branch:** the Release workflow refuses any ref but `main`, so an image tag is always a commit
   that passed CI on `main`.

### - [ ] S6: one-time server setup script

**Files:** create `deploy/server-setup.sh`. Independent of S3–S5.

Run once as root on a fresh Ubuntu 24.04 (R6). Idempotent (a second run changes nothing and doesn't fail):

1. Refuse to go on if `/root/.ssh/authorized_keys` is empty (it is what the new user gets — no key, no way in).

3. Docker Engine + compose plugin from Docker's apt repository (docs.docker.com/engine/install/ubuntu), not snap.
4. User `deploy` (no password, `--disabled-password`) in groups `docker`; `/home/deploy/.ssh/authorized_keys` copied
   from root's, owner `deploy`, mode 600.
5. `/etc/ssh/sshd_config.d/10-bookedup.conf`: `PasswordAuthentication no`, `KbdInteractiveAuthentication no`,
   `PermitRootLogin no`; `sshd -t` then `systemctl reload ssh`.
6. `ufw default deny incoming`, `allow 22/tcp`, `80/tcp`, `443/tcp`, `443/udp`, `ufw --force enable`.
7. `fail2ban` with its default `sshd` jail on; `unattended-upgrades` on (security updates only, no auto-reboot).
8. `/opt/bookedup` and `/var/backups/bookedup`, owner `deploy`; `/var/log/bookedup-backup.log` owned by `deploy`;

**Check:** `bash -n`, `shellcheck`. Run it twice in a throwaway container to catch typos in the non-systemd parts:

nano .env              # DOMAIN=<domain>, ACME_EMAIL=<your email>, the two above, TELEGRAM_BOT_TOKEN, TELEGRAM_BOT_USERNAME (no @)
```

Keep a copy of `.env` in your password manager: losing `POSTGRES_PASSWORD` locks you out of the volume's database.

**R8. Backups cron is there:** `ssh deploy@<ipv4> cat /etc/cron.d/bookedup-backup` prints the 03:30 line (S6 wrote it).
The next morning `ls /var/backups/bookedup` has a dump and `/var/log/bookedup-backup.log` no error.

**R9. First deploy:** `deploy/deploy.sh deploy@<ipv4>` → ends with the health check passing. Caddy gets the
certificate on the first request (DNS from R4 must already point at the server, ports 80/443 open).

**R10. Webhook:**

```

**R11. Uptime ping:** UptimeRobot (free) or healthchecks.io → HTTP monitor on `https://<domain>/api/health`, every

**R12. Smoke:**

1. `deploy/smoke.sh <domain>` → all ok.
2. Browser: sign up an owner, sign out, sign in. Create the business (time zone, slug), a staff schedule, a service.
3. Phone, not signed in: `https://<domain>/book/<slug>` → pick a slot → «Confirm phone in Telegram» → the bot shows
   the same code as the page → share the contact → back on the page → book. The owner's calendar shows the booking;
   the client gets the Telegram message. `getWebhookInfo` still has no error.
4. Install the PWA from the phone; after the next deploy it offers the update.
5. Backups: `ssh deploy@<ipv4> /opt/bookedup/backup.sh && /opt/bookedup/restore-check.sh /var/backups/bookedup/<newest>`
   → counts ≥ 1.
