## Decisions (2026-11-26)

User's (don't re-ask):

- **D1** One VPS, Ubuntu 24.04, 2 vCPU / 4 GB, Docker Compose, Caddy in front with automatic HTTPS. No
  Kubernetes, Swarm, Terraform, PaaS, multi-region; monitoring is logs plus pings (uptime, backups).
- **D2** One domain for everything: the front's static files on `/`, the API on `/api` with the prefix
  stripped (as the front's `vite.config.ts` proxy does). Why: the back's CSRF check refuses writes from another
  origin, and the session cookies are `__Host-*`.
- **D3** Postgres 18, Redis, the API, the notifications worker (one process).
- **D4** Telegram is required (no bot → no online booking, E7b D7): token and username from @BotFather,
  `TELEGRAM_WEBHOOK_SECRET` set, webhook per `docs/notifications.md`. WhatsApp, email, Web Push stay **off** (email
  comes with the password reset, P1 below).
- **D5** Production env: `NODE_ENV=production`, `APP_URL=https://<domain>`, `TRUST_PROXY=1`,
  `SESSION_COOKIE_SECURE=true`. Secrets never in git.
- **D6** Deploys are started by hand. No auto-deploy from `main`.
- **D16** Friends are in Europe, Georgia and Thailand → the server is in Germany or Finland (Hetzner).
- **D17** The test's data is **kept** when E11 launches: no wipe. Every migration from now on runs on real data
  (`back-prisma`: no destructive change without a data step).
- **D18** Swagger stays public at `https://<domain>/api/docs` (see D12).
- **D19** Nothing is lost for good (the user, 2026-11-26) — D14.
- **D20** Up to one hour of data may be lost in a crash (hourly dumps); no WAL archiving.
- **D21** Sentry and PostHog stay off for now. So the site sets only the cookies it needs to work (session, sign-in,
  language) — no analytics, no cookie banner (P2 relies on it; turning either on later changes P2's texts).
- **D22** Password reset (P1) ships **before** friends are invited (R16 waits for it).
- **D23** Terms of use and a privacy policy (P2) ship before friends are invited; the booking page shows a short
  note with a link.

Made while splitting (check in the PR):

- **D7 Images are built on GitHub Actions and pushed to GHCR; the server only pulls.** A `Release` workflow
  (`workflow_dispatch`, from `main` only) in each repo pushes `ghcr.io/fedos2589/bookedup-api:<sha>` and
  `ghcr.io/fedos2589/bookedup-web:<sha>`, `linux/amd64`. Why not build on the server: `npm ci` + `tsc` + `vite build`
  of two repos on 4 GB next to a running Postgres can run out of memory, the server would need git, Node and the
  sources, and a rollback would mean rebuilding an old commit. With images a rollback is «pull the previous sha»,
  seconds. The repos are public, so the packages are made public once (R2) and the server pulls without a token.
  The server is **x86 (amd64)**, not ARM: one platform, no multi-arch build.
- **D8 The notifications worker runs inside the one API container** (`NOTIFICATIONS_WORKER=true`, the default).
  One container = one process = one worker.
- **D9 Migrations run from the API image itself:** `prisma` and `dotenv` (which `prisma.config.ts` imports) move
  to `dependencies`, the image keeps `prisma/` and `prisma.config.ts`, and the deploy runs
  `docker compose run --rm api npx prisma migrate deploy` before starting the new API. One image, one tag.
- **D10 `btree_gist` needs no extra grant.** The compose Postgres user (`POSTGRES_USER`) is the cluster's superuser,
  and `btree_gist` is a trusted extension anyway (Postgres ≥ 13), so `CREATE EXTENSION` in
  `20261111134528_schedule` runs under `migrate deploy`. S1's check proves it on an empty database.
  **Known debt, accepted for the test:** the API connects as that superuser too, so an SQL injection would own the
  cluster (`COPY … TO PROGRAM`). Before E11: a migration owner role and an app role without `SUPERUSER`.
- **D11 The web image is `caddy:2-alpine` with the front's `dist/` in `/srv`;** the Caddyfile lives in the back's
  `deploy/` (next to the compose file and the domain) and is mounted.
- **D12 Swagger at `https://<domain>/api/docs-json`.** The back serves it at `/api/docs*` itself (`main.ts`), so Caddy
  passes `/api/docs*` through **without** stripping; everything else under `/api/` is stripped.
- **D13 Deploy is one command from the laptop:** `deploy/deploy.sh deploy@<ip> [api-sha|-] [web-sha|-]` copies
  `deploy/` (never `.env`), checks both images exist, takes a backup (D14), pulls, migrates, restarts, waits for
  health, and only then records the new images in `.env` and logs the release. An omitted sha (or `-`) keeps what
  the server runs now — not the head of `main`, which often has no image (Release is by hand, D6); the first deploy
  names both. Rollback = the same command with the previous shas from `releases.log`. **Migrations are not rolled
  back:** rolling back across a migration the old code can't read means restoring the backup taken by that deploy.
- **D14 Backups — nothing lost for good, at most the last hour:**
  - **The database is the only state.** No file uploads in the API; Redis holds only the queue (the notifications'
    outbox is in Postgres); Caddy's certificates are re-issued; images are in GHCR, code in GitHub. Secrets are in
    `.env` and `api.env` — their copies live in the password manager (R8).
  - **Hourly** `pg_dump -Fc`, and one before every deploy. Kept on the server 48 h (fast restore) **and** sent
    off-site with **restic** to an S3-compatible bucket at **another company** (Backblaze B2): a dead disk, a deleted
    server or a blocked Hetzner account loses nothing. Hetzner's own backups are deleted together with the server,
    so they are an extra, not the plan. restic encrypts on the server; the bucket never sees plain data.
  - Kept off-site: 48 hourly, 30 daily, 12 weekly, 11 monthly (`restic forget --group-by host,tags`: every hourly
    dump has its own file name, and restic's default grouping by `host,paths` would put each snapshot in a group of
    its own and never forget anything). With the 30 days of Object Lock below, deleted data leaves the off-site
    copies within **13 months** at most — the number the privacy policy (P2) states.
  - **A compromised server can't wipe the history: B2 Object Lock.** The bucket is created with Object Lock and a
    default retention of **30 days, governance mode**; the server's key has no `bypassGovernance` (nor
    `writeBucketRetentions`/`writeFileRetentions`). restic deletes on its own (lock files, `forget`, `prune`): on a
    locked, versioned bucket such a delete only hides the file, and every version stays readable for 30 days whatever
    the server does. A lifecycle rule removes hidden versions after 30 days, once their lock has run out. Why not «a
    key without `deleteFiles`»: restic can't run without deleting, and adding the right back later would drop the
    guarantee silently. S6 checks restic against a locked MinIO bucket; R11 against B2.
  - **Backups that silently stop are caught:** each successful hourly run pings healthchecks.io; no ping for 2 h →
    an alert. A **weekly restore check from the bucket** (not from the local copy) restores the newest snapshot
    into a scratch database, counts rows, and pings a second check.
  - **The full disaster is rehearsed once** before friends come (R15): the database is restored on the laptop using
    only what is in the password manager (restic password, B2 key) — no access to the server.
  - Loss of up to one hour is accepted for the test. Minutes instead of an hour needs WAL archiving (WAL-G) —
    not planned (D20).
  - restic runs from the pinned image `restic/restic:0.17.3` (same on the laptop and the server, nothing to install).
- **D15 A separate Telegram bot for the server.** Setting a webhook turns `getUpdates` off, and the dev API polls
  (`telegram-polling.ts`): one bot can't serve both.

## Global constraints

- Nothing in `src/` changes, except S0's logger config. If another task finds it must, stop: it is a separate task.
- No secret in git: `deploy/.env.example` holds names and comments only; `.env` is in `.gitignore` already.
- Images: `ghcr.io/fedos2589/bookedup-api:<full sha>`, `ghcr.io/fedos2589/bookedup-web:<full sha>`, lowercase owner.
- Every shell script: `#!/usr/bin/env bash`, `set -euo pipefail`, a usage line on wrong arguments, works from any
  current directory (`cd "$(dirname "$0")"`; a path argument is made absolute with `realpath` **before** the `cd`),
  passes `bash -n` and `shellcheck` (if `shellcheck` is not installed, say so in the commit message's body). Scripts
  on the server read `.env` with `set -a; . ./.env; set +a`.
- restic always runs through one wrapper: `docker run --rm --user "$(id -u):$(id -g)" … restic/restic:0.17.3
--no-cache …` — the image runs as root otherwise, and what it restores couldn't be deleted by `deploy`.
- `backup.sh` and `offsite-check.sh` hold one lock for their whole run (`exec 9>.backup.lock; flock -w 900 9`,
  in the script's directory; `deploy/.backup.lock` is in `.gitignore`): a deploy's backup, the hourly one and the
  weekly prune never meet on restic's exclusive lock.
- Compose files: every service `restart: unless-stopped` and the json-file log driver with `max-size: 10m`,
  `max-file: 5`. Images pinned to an exact version (`postgres:18.<minor>-alpine`, `redis:7.<minor>-alpine`, the
  current ones when the task runs) — a `docker compose pull` in every deploy must not upgrade the database by itself.
- GitHub Actions pinned to a major version (`actions/checkout@v5`, `docker/…-action@v<current major>`).
- Checks need Docker running locally. Commit messages via `git commit -F - <<'EOF'`.

## Review focus (for the Opus review of both PRs)

1. **Docker publishes ports past ufw.** Only `web` may have `ports:`; postgres and redis none.
2. **CSRF and the real client IP through Caddy:** `reverse_proxy` keeps the `Host` header (the back compares
   `Origin` with it) and sets `X-Forwarded-For` itself, ignoring a client's one (no `trusted_proxies`) — so with
   `TRUST_PROXY=1` rate limits count by the real IP and a client can't pick its own.
3. **The SPA fallback must not hide a missing chunk:** an old `/assets/x-<hash>.js` gets 404, not `index.html`
   with 200. Everything outside `/assets/` is `no-cache` — `/`, every SPA route (`/book/<slug>`), `sw.js` and the
   rest — matched by path, not by `/index.html` (Caddy runs `header` before `try_files`).
4. **A backup that fails must look failed:** a failed `pg_dump` or `restic` exits non-zero, sends no success ping,
   leaves no file with a real name; a dump is checked non-empty before it goes off-site.
5. **Release from a branch:** the Release workflow refuses any ref but `main`.
6. **No secret in the logs:** the `Cookie`, `Set-Cookie`, `Authorization` and Telegram secret headers are redacted
   (S0).
7. **A failed deploy leaves the server as it was:** `.env` names the new images only after the health check.

## P1. Password reset by email (branch `e21/password-reset` in each repo, after E21's deploy is merged)

**Goal:** an owner or staff member who forgot the password sets a new one through a link sent to their email.
Before friends are invited (D22).

### Decisions (2026-11-26, check in the PR)

- **D24 The link:** `<APP_URL>/reset-password/<token>`, the token `newRandomToken()` (256 bits), only
  `hashRandomToken()` stored. Lives **1 hour**, works **once**, and only the newest link of a user works (a new request
  deletes the older ones). A used link: all sessions of that user end (whoever knew the old password is out), the
  answer is 204 and the front goes to sign-in — no automatic sign-in from a link.
- **D25 `POST /auth/password-reset` always answers 204**, for an unknown email too. Sign-up does tell that an email
  is taken (back-api-contract), so this hides little — but it costs nothing, and it keeps the route from being a cheap
  «does this email exist» check. Limits: 10 an hour per IP (`@Throttle`), and a user gets at most one letter a minute
  (a newer request inside that minute is dropped silently — no mail-bombing).
- **D26 The letter is sent after the answer, not awaited** (`void send().catch(log with err)`): a slow Resend doesn't
  hold the request. Not a goal: equal timing for a known and an unknown email — the known one still runs a
  transaction, and sign-up tells that an email is taken anyway (D25); don't spend effort on equalising it. Not through
  the notifications outbox: a lost letter costs one more press of the button.
- **D27 One place talks to Resend:** the HTTP call moves out of `EmailChannel` into `src/mail/mailer.ts`
  (`Mailer.send({ to, subject, text }): Promise<SendResult>`); `EmailChannel` renders its message and calls it. Without
  `RESEND_API_KEY`: outside production the reset link goes to the log (info — how a developer resets locally); in
  production nothing is sent and a warning is logged (the start already warns that email is off; R18 turns it on).
- **D28 Turning Resend on also turns on E9's email notifications** (owners' `notifyEmail` is on by default; clients'
  email channel). Accepted: it is what E9 was built for.
- **D29 Everyone with a `User` row** (owner, admin, master) uses the same flow; there are no other kinds of password.
- **D30 The table is global** (no `business_id`, like `sessions`): `password_resets` — `id uuid` (uuidv7),
  `user_id uuid` → `users` ON DELETE CASCADE, `token_hash text UNIQUE`, `expires_at timestamptz`, `created_at`.
  Index on `user_id`. Expired rows go when that user asks again or resets; a tiny table, no purge job.

### Review focus (P1)

1. The token never reaches a log in production, a URL the back calls, or an error message; only its hash is stored.
2. A link is single-use under a race: two confirms with one token → one 204, one 404 (`DELETE … RETURNING`, not
   read-then-delete).
3. After a reset the old password fails and every earlier session of the user is gone — including the one in another
   browser.
4. The 204 of the request route is the same for a known and an unknown email — the same body, no cookie, and the
   time doesn't wait for Resend (D26: not equal to the millisecond).
5. The one-a-minute limit holds under a race: two parallel requests → one row, one letter (S13's lock).
6. The new password goes through the sign-up's `passwordSchema.min(8)` (including the byte limit).

- **D34 The texts are drafted by the executor from the outline below and read by the user in the PR** — not legal
  advice. Plain words, short sections, no invented facts: anything not in this outline or in `legalEntity.ts` is left
  out, not guessed.
- **D35 Two roles in the privacy policy:** for owner and staff accounts BookedUp decides why data is kept
  (controller); for a business's clients the **business** decides and BookedUp keeps the data for it (processor) —
  a client asks the business first, or writes to `privacy@`.

### Outline of the texts (what each must say)

**Privacy policy:** who (`legalEntity`); what is kept — accounts: email, name, password (hashed), language, sessions
(with the browser's description); clients: name, phone, email if the client gives it for reminders, notes the
business writes, Telegram chat id, bookings; **children and other dependents**: a client (a parent or guardian) or
the business can add a dependent — name, no phone — who is booked under the guardian's contacts (sports schools); the
guardian is responsible for adding them and can ask for them to be deleted like any client; server logs: IP address
and browser of each request, to find errors and limit abuse, kept until the logs rotate (a few days to a few weeks,
by volume), not in backups; cookies: only those the site needs to work (session, sign-in, language) — no analytics
(D21); why — run the account, make and remind about bookings, sign a client in by phone; where and who else holds
it — Hetzner (servers, Germany/Finland), Backblaze B2 (encrypted backups, EU), Telegram (messages and sign-in, if the
person uses it), Resend (letters: password reset, notifications); how long — while the account or the business's
client card exists; deleted data stays in encrypted backups up to 13 months (D14) and then is gone; rights — see, correct, delete, take a copy, object: write to
`privacy@`, answered by hand within 30 days; a complaint can go to the person's data protection authority; laws —
GDPR (people in the EU), Georgia's Law on Personal Data Protection, Thailand's PDPA; changes — the date at the top,
account holders told by email of big ones.

**Terms of use:** a free test before the paid version; no guarantee the service works or keeps data (backups lose at
most the last hour, D20); it can stop or be wiped with notice by email; the owner is responsible for having their
clients' consent to keep their contacts and for what they write about them; no unlawful use, spam or attempts to
break in — accounts doing that are closed; BookedUp's liability is limited to what the law allows; contact
`hello@<domain>`; the law of Georgia applies.
