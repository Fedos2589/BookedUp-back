# E5: режимы графика мастера — индивидуальные клиенты и группы

Дата: 2026-11-12. Статус: согласовано с владельцем продукта в чате, до плана.

## Зачем

Мастер задаёт, когда к нему можно записаться. Бизнесы бывают двух видов, и неделя у них
устроена по-разному:

- **индивидуальные клиенты** (барбер, ногти, ресницы): часы приёма по дням недели, нарезанные
  на слоты; на слот — один человек;
- **группы** (футбол для детей, большой теннис): именованное занятие в одни и те же дни и
  время, с лимитом мест; клиент видит «свободно 2 из 4».

Один мастер на одной неделе режимы не смешивает. Шаг 1 E5 (back PR #13) дал недельные окна,
разовые окна и отгулы, но без режима, без лимита мест и с другой семантикой разовых окон.
Этот документ — то, что меняется в бэке, ките и фронте, чтобы получилась страница «График».

## Цели

1. У каждого мастера свой режим: «Индивидуальные клиенты» или «Группы». По умолчанию —
   индивидуальные.
2. **Индивидуальные клиенты.**
   - Недельные часы приёма: по каждому дню недели — работает или нет, один или несколько
     интервалов (начало, конец), шаг слота.
   - Отдельные даты: на дату задаётся свой набор интервалов, и он **целиком заменяет** часы
     того дня недели. Дата без интервалов — выходной.
3. **Группы.**
   - Группа: название (обязательно), дни недели (один или несколько), время начала и конца
     (одно для всех её дней), лимит мест (целое ≥ 1).
   - Отдельные даты: отменить занятие группы на дату; добавить разовое занятие (название,
     дата, время, лимит мест).
4. **Отпуск** (с даты по дату, необязательная заметка) — в обоих режимах; это уже
   существующий `TimeOff`.
5. Свободное время для записи (`GET /businesses/:id/slots`) считается по режиму мастера и
   отдаёт для каждого слота лимит мест и число занятых.
6. Страница «График» в кабинете (вариант A с макета): выбор мастера, переключатель режима,
   разделы выбранного режима, отпуск.

Макет: [`2026-11-12-e5-schedule-mockup.html`](2026-11-12-e5-schedule-mockup.html), вариант
A (вариант B отклонён); на макете оба режима на одной странице — в жизни показывается только
раздел выбранного режима. Таблица недельных часов — по скриншоту владельца: строка на день
недели — галочка, название дня, начало, конец, «+» (ещё интервал), корзина у второго и
следующих интервалов; невыбранный день — «Суббота — недоступно»; внизу «Сохранить» /
«Отменить». Отдельные даты — список «Дата · Начало · Конец» с «+».

## Не цели

- Записи клиентов (E6/E7). Пока записей нет, «занято» всегда 0 — клиент увидел бы
  «свободно 4 из 4». Поле в API есть уже сейчас, чтобы E6 не менял контракт.
- Публичная страница записи (E7) — здесь только кабинет.
- Что происходит с записями при изменении группы или часов — решается в E6.
- Цена, услуги, длительность по услуге (E4 отменён).
- Буферы между слотами (сняты в шаге 1).

## Анти-цели (провал, даже если «работает»)

- Мастер в режиме «Группы» видит поля шага слота, а в режиме «Индивидуальные» — лимит мест:
  интерфейс показывает только свой режим.
- Группа на «Вт, Чт» показывается двумя карточками или правится в двух местах.
- Отдельная дата в режиме часов оставляет часть недельных часов того дня.
- Смена режима молча стирает то, что мастер уже заполнил.

## Решения

Решения владельца — без пометки; мои — помечены _(моё решение)_.

### Режим

- `Staff.scheduleMode`: `hours` | `groups`, по умолчанию `hours`.
- Меняет тот, кто может менять график этого мастера (те же правила, что у недельных окон:
  `StaffService.authorizeChangeOf`).
- Смена режима ничего не удаляет: данные другого режима хранятся и не участвуют в расчёте
  слотов _(моё решение)_. Вернул режим — всё на месте.

### Режим «Индивидуальные клиенты»

- Недельные окна — существующие `WeeklyWindow` и `PUT …/weekly-windows` (вся неделя одним
  запросом). Поле `title` в этом режиме интерфейс не показывает и не шлёт.
- **Отдельная дата** — новая сущность «день-замена» _(моё решение о форме)_: мастер, дата по
  часам бизнеса (`YYYY-MM-DD`), список интервалов `{startMinute, durationMinutes,
slotMinutes}` (может быть пустым — выходной). Одна запись на мастера и дату. Слоты дня-замены
  принадлежат этой дате; недельные слоты, которые **начинаются** в эту дату, не выдаются. Окно,
  начатое накануне и уходящее за полночь, остаётся (слот принадлежит дню, в который
  начинается — правило шага 1).
- API: `GET …/day-overrides` (не прошедшие, по дате), `PUT …/day-overrides/:date` (создать или
  заменить), `DELETE …/day-overrides/:date`. Интервалы одной даты не пересекаются — 400, как у
  недели.
- `OneOffWindow` и его маршруты удаляются _(моё решение)_: их роль делят день-замена и
  разовое занятие группы. Продакшена нет (E1 отложен), данных терять негде; миграция
  удаляет таблицу.

### Режим «Группы»

- **Группа**: `id`, мастер, `title` (1–100 символов), `weekdays` (непустое множество 1–7,
  ISO), `startMinute`, `durationMinutes` (1–1440), `capacity` (1–1000 _(моё решение о
  верхней границе)_). Одна группа — одна запись, сколько бы у неё ни было дней.
- Группы одного мастера не пересекаются по времени ни в один день недели — 400 с путём до
  поля, как у недельных окон _(моё решение: мастер не ведёт две группы сразу)_.
- API: `GET/POST …/groups`, `PUT/DELETE …/groups/:groupId`.
- **Отмена занятия**: группа + дата по часам бизнеса, одна на пару. API:
  `PUT/DELETE …/groups/:groupId/cancellations/:date`; список отмен — в ответе `GET …/groups`
  у каждой группы (не прошедшие) _(моё решение)_.
- **Разовое занятие**: мастер, `title`, `startsAt`, `endsAt` (не длиннее суток), `capacity`.
  Не пересекается с другими разовыми занятиями мастера и с занятиями его недельных групп в
  эту дату, кроме отменённых — 409 с кодом, по которому фронт скажет «в это время идёт
  „Футбол“ — сначала отмени его на эту дату». Так слоты режима групп никогда не
  пересекаются. Обратное тоже проверяется: группу, чьё новое время задевает разовое занятие
  впереди, сохранить нельзя (409) _(моё решение)_. API: `GET/POST …/one-off-sessions`,
  `DELETE …/one-off-sessions/:id`.

### Слоты

- `GET /businesses/:id/slots` берёт у каждого мастера только источники его режима:
  - `hours`: недельные окна, кроме дней-замен; слоты дней-замен;
  - `groups`: занятия групп по их дням, кроме отменённых дат; разовые занятия.
    Отпуск вычитается в обоих режимах.
- Каждый слот получает `capacity` (в режиме часов 1) и `booked` (пока 0), а также `groupId`
  (у слота группы) и `oneOffSessionId` (у слота разового занятия); оба `null` в режиме часов
  _(моё решение: E6 привяжет запись к занятию, не меняя контракт)_. `title` — название группы
  или разового занятия.
- Заполненный слот (`booked >= capacity`) остаётся в ответе — страница записи покажет «мест
  нет» _(моё решение)_. До E6 такого не бывает.
- Правило «слоты мастера не пересекаются» из шага 1 остаётся.

### Кит (TedUI)

- **`TimePicker`** — новый компонент: поле времени «ЧЧ:ММ», 24 часа, значение — минуты после
  полуночи или `null`. Строится на `InputShell` (подпись, подсказка, ошибка). Как выбирать
  время на телефоне — решает исполнитель (нативный `type="time"` даёт колесо на iOS, это
  кандидат).
- Дни недели для группы — существующий `TagSelect` с `multiple`; новый компонент не нужен.
- Всё остальное на странице — из существующих компонентов (`Checkbox`, `Button`,
  `IconButton`, `Input`, `Modal`, `DatePicker`, `TabsRounded`/`Tabs` для переключателя).
  Чего не хватит — сначала в кит (правило проекта).

### Фронт (BookedUp-front)

- Маршрут `/schedule` — дочерний в `cabinet`, пункт меню «График» (en: «Schedule»).
- Вверху выбор мастера — для того, кто может менять чужие графики; мастер видит только свой
  график _(моё решение)_. Под ним переключатель режима.
- **Индивидуальные клиенты**: таблица из макета — строка на день недели с галочкой «работаю»,
  интервалами (начало/конец через `TimePicker`), «+ интервал», удаление интервала; шаг слота
  — один на мастера в интерфейсе _(моё решение; API хранит его на интервал, интерфейс пишет
  одно значение во все)_. «Сохранить» / «Отменить» внизу — неделя уходит одним `PUT`. Ниже —
  «Отдельные даты»: список, «+ Дата» (дата, интервалы или «выходной»).
- **Группы**: карточки «Футбол, дети 7–10 · Вт, Чт · 15:00–16:00 · до 12 человек», «+
  Группа» (форма: название, дни, начало, конец, мест), правка и удаление. «Отдельные даты»:
  отмена занятия на дату, «+ Разовое занятие».
- **Отпуск** — раздел в обоих режимах: с даты по дату (обе включены, целые дни по часам
  бизнеса), заметка. Форма — только `DatePicker`, без времени; API не меняется — фронт шлёт
  полночь первого дня и полночь дня после последнего. Запись, которая покрывает часть дня
  (создана через API), показывается с временем, удалить её можно _(моё решение)_.
- Формы вызывают `useUnsavedInput` (правило PWA-обновлений).
- Тексты en + ru.

## Ограничения

- Время и даты — по часам бизнеса; правила шага 1 (переход на летнее время, окна через
  полночь, `clockOf`) сохраняются, тесты на них остаются зелёными.
- Мультиарендность: каждая новая таблица несёт `business_id`, связи внутри бизнеса —
  составными ключами (AGENTS.md бэка).
- Кит ничего не знает о BookedUp (AGENTS.md кита); `TimePicker` получает story и, если в нём
  есть логика разбора времени, тесты.
- Каждый шаг — отдельная ветка и PR в `main`, следующий начинается после ревью.

## Порядок работ

1. **Бэк** (эта ветка `e5/schedule-modes`): режим, день-замена, группы, отмены, разовые
   занятия, `capacity`/`booked`/`groupId` в слотах, удаление `OneOffWindow`.
2. **Кит**: `TimePicker`, релиз минорной версии.
3. **Фронт**: страница «График», режим «Индивидуальные клиенты» и отпуск.
4. **Фронт**: режим «Группы».

## Оставлено исполнителю

- Схема хранения интервалов дня-замены (дочерняя таблица или JSON) и множества дней
  группы (`smallint[]` или дочерняя таблица).
- Внутреннее устройство `TimePicker` и поведение на телефоне.
- Раскладка формы группы и дня-замены (модалка или раскрытие на месте).
- Коды и тексты ошибок валидации — по образцу шага 1.
